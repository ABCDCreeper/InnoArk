## 0. 先看全局：这套系统到底在干什么

一句话：**一台树莓派同时连着心率手环、摄像头和刷卡器，一边把数据实时推给教室触摸屏上的网页，一边把数据上传到云端。**

整个链路可以拆成四段：

```
① 采集          ② 汇聚                ③ 本地呈现            ④ 上云
BLE 手环   ┐                       ┌  WebSocket → 浏览器（教师端）
USB 摄像头 ├→ asyncio 队列 → 广播/打包 ┤
PN532 刷卡 ┘                       └  MQTT → 云端（可离线缓冲）
```

几个贯穿全文的关键词，理解了它们，技术文档里绝大多数选择都不用再背：

| 关键词 | 含义 | 体现 |
|---|---|---|
| 异步 | 一棵线程里"等人"的时间拿去做别的事 | asyncio、协程、队列 |
| 轻量 | 树莓派是 4 核 ARM、4GB 内存的小机器，大框架跑不动 | Flask、SQLite、Haar Cascade |
| 离线 | 教室网络随时可能断 | 离线缓冲、断线重连、心跳 |
| 零配置 | 现场没人会调试服务器 | Hash 路由、SQLite、Kiosk 自启 |
| 隐私 | 画面里有学生脸 | 只传特征向量，不传视频 |

以下术语按主题排列，与技术文档的章节顺序基本对应。

## 1. 编程语言与并发机制

对应技术文档 §1.1、§1.6、§2、§6.1–§6.2。

### 1.1 语言与运行环境

- **Python**：一种语法接近自然语言的编程语言。本项目里，树莓派上的传感器程序、Flask 后端、部署脚本都是 Python。
- **CPython**：Python 的官方实现（用 C 写的解释器）。平时说的"Python"几乎都指它；GIL 就是它引入的限制。
- **树莓派 4B（Raspberry Pi 4B）**：信用卡大小的单板计算机，本项目用它当"边缘终端"——放在教室里、直接连传感器的那台机器。它用 ARM 架构 CPU、4GB 内存，性能大致相当于一部低端手机。
- **ARM Cortex-A72**：树莓派 4B 的 CPU 核心型号。ARM 是手机、嵌入式设备的主流架构，**和普通 PC 的 x86 不通用**——同一个软件常常要为 ARM 单独编译一份，这就是文档里 MediaPipe 装不上的根因。
- **ARM64 / aarch64**：ARM 的 64 位版本。树莓派 4B 的系统是 64 位，很多深度学习库只提供 x86 的安装包，ARM64 上要么没有、要么得自己编译。
- **边缘终端 / 边缘计算（edge）**：把计算放在数据产生的地方（教室里的树莓派），而不是全部传到云端再算。好处是响应快、省带宽、隐私数据不出设备。项目里 `edge/` 目录就是这套东西。
- **I/O 密集 / CPU 密集**：任务的两大类型。I/O 密集指时间主要花在"等外部返回"（等网络、等设备）；CPU 密集指时间主要花在"算"。三类传感器都属前者，所以适合异步——这是技术文档选 asyncio 的第一条理由。

### 1.2 异步与事件循环

- **asyncio**：Python 标准库里的异步 I/O 框架。它让一个线程同时"照看"很多等待中的任务。
  - 通俗理解：一个服务员同时管十桌客人——给 A 桌下单后不站在旁边等厨房，而是先去 B 桌点单，谁好了再回来端给谁。
  - 文档中的位置：`edge/__init__.py` 里用一个事件循环同时跑 3 个传感器协程、1 个 WebSocket 服务和 1 个 MQTT 客户端。
- **协程（coroutine）**：用 `async def` 定义的函数，特点是"可以中途暂停、稍后接着跑"。
  - 通俗理解：一本能随时夹上书签合上、之后再从书签处继续读的书。普通函数必须一口气读完。
- **事件循环（event loop）**：异步程序的"总调度台"，不停检查"谁等待的事情好了、现在该轮到谁跑"。
- **`await`**：协程里"我要等一下，先把控制权还回去"的关键字。`await` 的后面通常是一个"需要时间才能出结果"的操作（网络收发、定时等待、设备读取）。
  - **最容易踩的坑**：`await` 不是可有可无的装饰。调用一个 `async def` 函数只会得到"一个还没开始执行的待办"，只有 `await` 它才真正执行。技术文档 §5.2 里 MQTT 消息"既不发出也不报错"，就是漏了 `await`：

    ```python
    await client.publish(...)   # 正确：真的发出去
    client.publish(...)         # 错误：造了一个协程对象就扔了，静默失败
    ```

- **协作式并发（cooperative concurrency）**：任务只在代码明确写 `await` 的地方让位，操作系统不会强行打断它。与之相对的是"抢占式"。
  - 好处：没有锁的开销、没有随机切换，代码行为可预期。
  - 代价：谁写出一个不 `await` 的死循环，整个事件循环都会卡住（业务代码里要避免长时间纯计算）。
- **让出控制权（yield control）**：`await` 时把执行权交还事件循环，让它去跑别的协程；等自己的事情完成后再被唤醒。
- **asyncio.Queue**：见 1.4。
- **asyncio.TaskGroup**：见 1.4。

### 1.3 其他并发方案，以及它们为什么没被选中

- **多线程（multithreading）**：同一进程里开多条执行流，共享内存。切换快，但多个线程同时改同一份数据时必须加锁。
- **多进程（multiprocessing）**：开多个独立进程，各有各的内存。互不干扰，但数据不能直接共享。
- **GIL（Global Interpreter Lock，全局解释器锁）**：CPython 的机制——同一时刻只有一个线程能执行 Python 字节码。
  - 影响：多线程在"算得多的任务"上几乎无法并行，还会平白增加"抢锁"开销；而本项目是 I/O 密集，用线程也换不来多少好处。
  - 补充：较新的 Python 版本开始提供可关闭 GIL 的实验性构建，但生产环境仍以带 GIL 的版本为准。
- **线程上下文切换开销**：操作系统从一条线程换到另一条时，要保存寄存器、切换栈，本身要花时间。线程越多，这部分"纯开销"越大。
- **跨进程通信（IPC）**：两个进程之间传数据只能靠管道、共享内存、socket 等通道，而且要先序列化。多进程方案里，共享"队列"和"设备状态"就得额外写一套 IPC，复杂度远高于同进程内直接使用 `asyncio.Queue`。
- **内存争用 / 锁争用**：多条执行流抢同一份资源或同一把锁时相互等待。技术文档用"没有 GIL 争用"来说明异步在这里的优势。

### 1.4 数据传递与同步

- **生产者—消费者模式（producer–consumer）**：做数据的一方和用数据的一方不直接打交道，中间放一个队列。
  - 通俗理解：后厨和传菜口。厨师把菜放到窗口，服务员从窗口取走，两边不用互相等。
  - 文档中的位置：三个传感器是生产者，WebSocket 广播循环是唯一消费者（§1.6）。
- **asyncio.Queue**：异步版的"传送带"。生产者 `await queue.put(x)` 放数据，消费者 `await queue.get()` 取数据。
  - 文档中的位置：`sensor_queue = asyncio.Queue(maxsize=100)`。
- **有界队列（bounded queue）/ `maxsize`**：给传送带设定容量上限。容量满时，`put()` 会一直等待，直到有人取走。
- **背压（backpressure）**：消费者跟不上时，有界队列自动让生产者"慢下来"，内存不会无限增长。
  - 通俗理解：水管的阀门。下游堵了，上游自然灌不进去，而不是把管子憋爆。
- **临界区**：同一时刻只允许一个执行流进入的那段代码（通常是读改写共享数据的那几行）。
- **竞态条件（race condition）**：两个执行流插队操作同一份数据，最终结果取决于谁先谁后，表现出来像"偶发的随机 bug"。
  - 文档中的例子：心率回调正在往缓冲区写入，聚合任务同时在读取并清空，可能读到写了一半的数据，或者把刚写入的间期连同清空一起丢掉（§2.2、§6.1）。
- **asyncio.Lock（异步锁）**：保证同一时刻只有一个协程能进入临界区。
  - 通俗理解：公共洗手间的门锁。后来者要在门外排队。
  - 文档中的用法：所有对 RR 缓冲区的读写都先 `async with self._rr_lock`，但只锁"拷贝列表"这一小段（微秒级），不锁后面的计算和网络发送，避免影响 BLE 通知的接收。
- **快照（snapshot）/ `copy()`**：在锁内把数据复制一份，出锁之后慢慢用副本处理。目的是缩短持锁时间。
- **asyncio.TaskGroup**：Python 3.11 引入的语法糖，把一组协程任务放进 `async with` 里统一启动和收尾；其中一个任务抛异常时，其余任务会被一起取消，不会留下"孤儿任务"。
  - 文档中的位置：`edge/__init__.py` 用 `async with asyncio.TaskGroup() as tg:` 同时启动 3 个传感器和广播循环。
- **协程任务（Task）**：协程被事件循环接管后的"运行实体"；`tg.create_task(...)` 创建的就是它。

### 1.5 数据表示与配置

- **序列化（serialize）**：把内存中的对象（比如一个数据类实例）变成可以传输或存储的字节/文本。反向操作是**反序列化（deserialize）**。
  - 文档中的位置：广播前把数据 `json.dumps` 成字符串；打包成统一数据包后发布到 MQTT。
- **JSON**：一种通用文本数据格式，形如 `{"key": "value"}`。人可读、各语言都支持，是 WebSocket 与 MQTT 消息的载体。
- **数据类（dataclass）**：Python 里专门用来"装一组字段"的类，写法简洁、自带比较与打印。
  - 文档中的位置：`EdgeConfig` 存放设备配置；传感器采集结果也是数据类，用 `dataclasses.asdict()` 转成字典后再序列化。
- **环境变量**：由操作系统传给程序的键值对，用来在不改代码的前提下改配置。
  - 文档中的位置：`INNOARK_CAMERA_DEVICE` 用来覆盖摄像头设备号，方便换机器时现场调整。

## 2. 后端框架与数据库

对应技术文档 §1.2、§1.4、§6.6、附录 A。

### 2.1 Flask 及其零件

- **Flask**：轻量级 Python Web 框架，写几个函数、挂上 URL 就能对外提供接口。
  - 文档中的位置：承载用户认证、项目 CRUD、题库、专注记录等业务接口；树莓派上运行内存约 20MB，启动低于 1 秒。
- **路由（route）**：URL 与处理函数的对应关系。例如 `POST /sessions` 对应登录处理函数。
- **蓝图（Blueprint）**：Flask 把路由按业务拆到多个文件、再统一注册回主应用的机制。
  - 通俗理解：一本书拆成若干章节分别写，最后装订成一册。文档用它组织 10 个以上路由模块。
- **WSGI（Web Server Gateway Interface）**：Python 里"Web 服务器"和"Web 框架"之间的标准接口。Flask 应用就是一个 WSGI 应用；技术文档里 `main.py` 把 Flask 挂到 aiohttp 上，就是通过 WSGI 适配层实现的，让异步服务和同步业务接口共用一个进程与端口。
  - **ASGI** 是它的异步版本（支持 WebSocket、异步请求），aiohttp 属于这一类。文档选择"异步服务 + WSGI 挂载"而不是把整个后端改成 ASGI，是为了不给树莓派增加改造与运行成本。
- **Werkzeug**：Flask 的底层 HTTP 工具库（请求/响应对象、路由匹配等）。
- **Jinja2**：Flask 自带的网页模板引擎（把变量填进 HTML）。本项目前端是 Vue 单页应用，模板只作兜底。
- **Click**：Python 的命令行参数解析库，Flask 用它实现 `flask run` 之类的命令。
  - 文档提到这三个库，是在说明"Flask 的直接依赖很少、装起来轻"。
- **应用工厂（application factory）**：用一个 `create_app()` 函数"现场组装"并返回 Flask 应用，而不是在模块顶层直接创建。好处是可以按不同配置创建多个实例，也便于写测试。文档附录 A 中 `backend/app/__init__.py` 就是它。
- **请求级连接（per-request connection）**：每次 HTTP 请求新建一个数据库连接、请求结束即关闭。见 2.3。

### 2.2 被对比过的其他 Python Web 框架

- **Django**：功能齐全的"全家桶"框架，自带 ORM、后台管理（**admin**）、中间件栈。功能全但重，对树莓派偏奢侈。
  - **ORM（Object-Relational Mapping，对象关系映射）**：用 Python 类和对象操作数据库表，不用手写 SQL。
  - **admin 后台**：Django 自带的管理网页，能直接增删改数据库内容。
  - **中间件（middleware）**：请求进来、响应出去时要穿过的层层处理（鉴权、日志、会话等），层数越多开销越大。
- **FastAPI**：现代的异步 Python 框架，基于 Starlette + Pydantic。
  - **Pydantic**：数据校验库，先声明每个字段的类型，收到的数据自动校验并转换；FastAPI 靠它生成接口文档与报错信息。
  - 文档认为它的启动和序列化开销比 Flask 大，因此没有采用。

### 2.3 存储：SQLite

- **SQLite**：嵌入式关系型数据库，"一个文件就是一个数据库"，不需要安装和运行数据库服务进程。
  - 通俗理解：Access 那种单文件数据库，但以程序库的形式被代码直接调用。
  - 文档中的位置：`innoark.db` 存用户、项目、题库、专注记录；数百用户规模下文件小于 1MB。
- **嵌入式数据库**：以库的形式"长"在程序里的数据库（SQLite、DuckDB 等），与 MySQL/PostgreSQL 这类需要独立守护进程和独立端口的"客户端—服务器"数据库相对。
- **WAL（Write-Ahead Logging，预写日志）**：SQLite 的一种日志模式。修改数据前先把改动写进日志文件，再择机合并回主库。
  - 关键收益：**读操作不会阻塞写操作，写操作也不会阻塞读操作**，因此"多个人同时查询"和"一个人写入"可以并存。
  - 代价：写与写之间仍然互斥（见下条）。
- **写操作串行化**：SQLite 同一时刻只允许一个写事务，其余排队。文档的判断是：单次写入低于 10ms，在 50 人以内的场景完全够用。
- **事务（transaction）**：一组"要么全部成功、要么全部失败"的数据库操作。
- **SQLite 的线程约束**：SQLite 的连接对象默认只能在其创建的那条线程里使用，跨线程会抛 `SQLite objects created in a thread can only be used in that same thread`。
  - 原因：Flask 开发服务器默认多线程处理请求（`threaded=True`），而 SQLite 连接不是线程安全的。
  - 办法：**不共享连接**——每个请求独立建连接，用完关闭（§6.6）。
- **`g` 对象**：Flask 提供的"单次请求内到处可用的临时储物柜"，用来暂存这次请求的数据库连接。
- **`before_request` / `teardown_request`**：Flask 的两个钩子。前者在请求处理前执行（建连接放 `g`），后者在请求结束后执行（关闭连接），保证不泄漏。
- **MariaDB / PostgreSQL**：两种常见的数据库服务器。文档用它们做对比：在树莓派上要多占 100MB 以上内存和一个常驻进程，而 SQLite 几乎不占额外内存。

### 2.4 接口风格与鉴权

- **RESTful API**：一种接口设计风格——用名词复数表示资源、用 HTTP 方法表示动作（GET 查、POST 建、PUT 改、DELETE 删），每个 URL 代表一样东西。
- **CRUD**：Create / Read / Update / Delete，增删改查四类基本操作，文档用它概括后端的业务范围。
- **鉴权（authentication / authorization）**：确认"你是谁"以及"你有没有权限做这件事"。
- **token**：登录成功后服务器签发的凭证字符串。之后每个请求带上它，服务器据此认出用户，不必每次重发密码。
- **session token**：会话令牌，即上面这种"代表一次登录会话"的 token。文档附录 A 里 `auth.py` 负责的就是它的签发与校验；前端存在 `localStorage` 里。
- **开发入口（`run.py`）**：Flask 自带的简易开发服务器启动脚本，方便本机调试；生产环境由 `main.py` 与 systemd 接管。

## 3. 前端技术栈

对应技术文档 §1.3、§1.5、§4、附录 A。前端跑在树莓派接的触摸屏上，对体积和流畅度敏感，这决定了下面几乎每个选择。

### 3.1 框架与组件库

- **Vue 3**：主流的渐进式前端框架，用"组件"（一个 `.vue` 文件 = 结构 + 逻辑 + 样式）拼出页面。
- **组件（component）**：可复用的页面零件，比如一个任务卡片、一个弹窗。
- **Naive UI**：一套 Vue 3 组件库，提供表格、对话框、表单、菜单、通知等成品零件。
  - 选它的理由：支持**按需引入**（只打包用到的组件，不必全局注册），属性贴近原生 HTML 语义，团队上手快。
  - **按需引入**：只把实际用到的组件打进产物，未用到的在打包阶段被丢弃。
- **Element Plus / Ant Design Vue**：另外两套同量级的 Vue 组件库。文档提到它们是为了说明取舍——一个体积偏大，一个样式覆盖（改默认外观）比较麻烦。

### 3.2 构建与产物

- **ESM（ES Modules）**：浏览器原生的模块体系（`import` / `export`）。构建工具能根据静态的模块依赖做优化。
- **Vite**：前端构建工具。开发时用原生 ESM 提供"改完立即刷新"的热更新；构建时把代码压缩、拆分、合并。
- **tree-shaking**："摇树"——打包时把没有被引用到的代码抖掉，从而缩小体积。
- **gzip**：HTTP 传输前对内容做压缩的格式；浏览器收到后自动解压。文档中"产物低于 200KB"指的是压缩后的传输体积。
- **首屏加载**：用户打开页面到看见可用内容所花的时间。文档中本地 Nginx 提供静态文件时低于 2 秒。
- **fps（帧率）**：每秒渲染多少帧。60fps 是"操作跟手、动画顺滑"的常用基准。
- **SPA（Single Page Application，单页应用）**：整站只有一个 HTML 文件，切换页面由 JavaScript 局部替换内容，不整页刷新。本项目就是 SPA，因此才有下面的路由模式问题。

### 3.3 路由与部署路径

- **Hash 路由**：URL 里带 `#`，如 `/#/projects`。浏览器不会把 `#` 后面的内容发给服务器，这段路径完全由前端自己解析。
  - 好处：服务器只需要"把静态文件发出去"，不用为前端路由配置任何回退规则；应用部署在根路径还是子路径都一样。
  - 代价：URL 里多一个 `#`；在全屏触摸终端里用户从不手输地址，所以几乎无感。
  - 代码对应 `createWebHashHistory`。
- **History 模式**：URL 干净（`/projects`），但请求会真的发给服务器。刷新或直接访问子路径时，服务器必须把未知路径回退到 `index.html`，否则 404。
  - 代码对应 `createWebHistory`。
- **Nginx**：常用的 Web 服务器，负责发静态文件、做反向代理。
- **`try_files`**：Nginx 指令，意思是"依次尝试这些文件/目录，都不存在就用最后一个"。History 模式的标配写法是 `try_files $uri $uri/ /index.html`。
- **`location /`**：Nginx 的路径匹配块，表示"所有以 `/` 开头的请求都交给这段配置处理"。
- **子路径部署**：把应用挂在 `https://host/innoark/` 而不是根路径。History 模式下所有前缀都要跟着改，容易出错；Hash 模式下不需要任何改动。
- **静态文件（static files）**：HTML、CSS、JS、图片这类不需要程序处理、直接原样返回的文件。

### 3.4 状态管理与登录时序

- **Pinia**：Vue 3 官方推荐的状态管理库，用来在任意组件间共享数据。
- **store**：Pinia 里的一块"全局数据仓库"，比如用户信息、登录状态、当前项目。
- **auth store**：专门存放认证相关状态的 store（`frontend/src/stores/auth.ts`），保存 token 与当前用户。
- **localStorage**：浏览器的本地键值存储，页面关闭后仍然存在。项目用它持久化 token，刷新页面还能保持登录。
- **导航守卫（navigation guard）**：Vue Router 在跳转页面前执行的检查钩子，通常用来判断"登录了没有、能不能进"，未登录就重定向到登录页。
- **时序问题（race）**：文档 §4.3 描述的现象——守卫可能在 auth store 初始化完成前就做出"未登录"的错误判断，于是登录成功后跳过去仍被拦回登录页。
  - 现做法：登录成功后 `setTimeout(..., 300)` 延迟 300ms 再跳，等状态更新传播完。
  - 更正统的做法：监听 store 的响应式变化（如 `watch`）再跳转，但文档判断 300ms 在这个场景下更简单可靠。

## 4. 部署形态：Kiosk 终端

对应技术文档 §4.2。设备是接在触摸屏上的树莓派，开机就应自动进入全屏页面，不给用户任何"操作系统"的痕迹。

- **Kiosk 模式（信息亭模式）**：浏览器全屏运行、没有地址栏与标签页的模式，常见于自助查询机、取号机。
- **Chromium**：Chrome 的开源版本，Linux 上常用的浏览器，本项目用它承载前端。
- **启动参数**：
  - `--kiosk`：进入全屏 Kiosk 模式，无地址栏、无窗口边框。
  - `--window-size=1920,1080`：固定窗口分辨率为 1920×1080，避免不同屏幕下布局错位。
  - `--start-maximized`：启动即最大化。
  - `--touch-events=enabled`：强制启用触摸事件，让触摸屏的手势和点击被正确识别。
- **`unclutter -idle 5`**：一个小工具，鼠标 5 秒不动就隐藏指针。触摸屏上不需要箭头一直杵着；不加 `-root` 参数是为了避免与某些窗口管理器的权限冲突。
- **`fonts-wqy-zenhei` / `fonts-wqy-microhei`**：两款开源中文字体（文泉驿正黑、文泉驿微米黑），装上才能正常渲染中文，否则界面会显示成方框。
- **`fonts-noto-color-emoji`**：彩色 Emoji 字体，保证表情符号正常显示。
- **屏幕保护 / DPMS**：X 的省电机制，闲置一段时间后自动黑屏。Kiosk 必须关掉，否则用户第一次来看到的就是黑屏。
  - **`xset`**：X 窗口系统下的显示设置命令，用它关闭屏幕保护与 DPMS。
- **开机自启**：树莓派开机后自动执行上述配置并打开 Chromium，用户不需要任何操作。

## 5. 通信协议

对应技术文档 §2.5、§3、§5。这一节是本项目的"血管"。

### 5.1 WebSocket（本地实时推送）

- **HTTP 短连接**：传统交互方式——浏览器问一次，服务器答一次，连接随即结束。服务器不能主动给浏览器发消息。
- **WebSocket**：在 HTTP 之上"升级"出来的一条长连接，之后双方可以随时互发消息。
  - 通俗理解：从"打一次电话问一句"变成"电话一直不挂"，服务器有事可以直接说。
  - 文档中的位置：树莓派把传感器数据实时推给教师端页面；服务端用 `aiohttp.web.WebSocketResponse` 实现。
- **握手（Upgrade）**：WebSocket 连接建立时先发一个 HTTP 请求，请求头里写 `Upgrade: websocket`，服务器同意后协议切换，此后不再按 HTTP 规则解析。
- **全双工（full-duplex）**：同一条连接上双向同时可发，不必轮流。
- **aiohttp**：Python 的异步 HTTP 客户端/服务器库，本项目用它同时提供 WebSocket 服务并托管 Flask（WSGI）。
- **`WebSocketResponse`**：aiohttp 中代表"一条已连接的 WebSocket"的对象；服务器把所有这类对象放进一个集合，就是"当前在线客户端名单"。
- **广播（broadcast）**：把一条消息循环发给名单里的每个客户端。
  - 文档中的要点：广播集中在一个协程里做，避免多个协程同时往同一条连接写数据（那会互相踩踏）。
- **`ConnectionResetError`**：对端突然断开（拔网线、关页面）时抛出的异常；捕获到就把该连接从名单里移除，避免一直往死连接上写。
- **心跳（heartbeat）/ ping-pong**：定时发一个极小的控制帧，用来确认对方还活着。
  - 通俗理解：打电话时"喂，还在吗？"
  - 文档中的位置：服务器每 30 秒发一次 ping，浏览器/客户端的底层库自动回 pong，不需要业务代码处理；发送失败即认为连接已断。
- **超时（timeout）/ `sensor_status`**：某一类传感器超过 15 秒没有数据，服务器广播一条状态事件，前端把对应指示灯标成"断开"。这是"数据陈旧"的判据，与上面的连接心跳是两回事：一个是链路是否活着，一个是设备是否还在产出。

### 5.2 MQTT（上传云端）

- **MQTT**：为物联网设计的轻量消息协议，采用发布/订阅模型。
  - 通俗理解：公共公告板。设备往某个"主题"贴消息，所有订阅了这个主题的人都能收到，发的人不需要知道谁在收。
  - 相对 HTTP 的优势：报文极小、长连接、适合不稳定网络与低功耗设备。
- **broker（消息代理）**：MQTT 的"公告板服务器"，负责接收发布、转发给订阅者。本项目只做客户端，broker 部署在云端。
- **topic（主题）**：消息的地址，像文件路径一样分层。文档中的格式是 `前缀/设备号/传感器类型`。
- **发布 / 订阅（publish / subscribe）**：发送方 `publish` 到主题，接收方 `subscribe` 主题。
- **QoS（Quality of Service，服务质量等级）**：
  - QoS 0：最多送达一次，可能丢。
  - **QoS 1**：至少送达一次，可能重复——本项目采用，因此数据包里带 `packet_id` 供接收端去重。
  - QoS 2：恰好送达一次，握手开销最大。
- **上行通道**：数据从设备往云端传的方向；反方向叫下行。
- **离线缓冲（offline buffer）**：断网时先把数据写进本地 SQLite 表，网络恢复后再按顺序补发。
  - 触发条件：MQTT 客户端未连接，或 `publish` 抛异常。
  - 通俗理解：快递员不上门时先把包裹码在仓库，路通了再送。
- **重试循环（retry loop）**：后台协程每 5 秒检查一次网络与待发队列。
  - 为什么是 5 秒：太短会变成高频空转、白耗 CPU；太长则积压严重、数据延迟大。
  - 补发失败时 `break`，留到下一轮再试，保证顺序不被打乱。
- **静默失败（silent failure）**：错误发生了却没有任何提示。文档里的典型例子是漏写 `await`，消息不发也不报错——这类问题最难排查，因为日志里什么都不缺。
- **aiomqtt（旧名 asyncio-mqtt）**：Python 的异步 MQTT 客户端库，2023 年改名。它的 `publish()` 是异步方法，必须 `await`（§5.2）。

### 5.3 蓝牙与 BLE（心率手环）

- **蓝牙（Bluetooth）**：短距离无线通信标准，用于连接手环、耳机等外设。
- **BLE（Bluetooth Low Energy，低功耗蓝牙）**：蓝牙的一个分支，专为"数据量小、要省电"的设备设计，手环、心率带、传感器都用它。
- **扫描（scan）**：主机在一定时间窗口内监听周围设备的广播包，把发现的设备列出来。
- **设备发现的两阶段策略**：先按"心率服务 UUID"精确过滤扫描，找到就用；找不到再退一步，按设备名关键词（"小米手环"、"Xiaomi"）匹配。这样既精准又能在不同型号手环上兜底。
- **GATT（通用属性配置文件）**：BLE 设备对外暴露数据的标准结构，像一棵树：服务 → 特征 → 值。
  - **服务（Service）**：一组相关功能的集合。**UUID `0x180D`** 就是标准的心率服务。
  - **特征（Characteristic）**：真正装数据的那个点，可以读、可以写、可以订阅通知。**UUID `0x2A37`** 是心跳测量特征。
  - **UUID（Universally Unique Identifier）**：一长串十六进制编号，用来唯一标识某个服务或特征。文档里写全的 `0000180d-0000-1000-8000-00805f9b34fb` 是蓝牙标准的"短 UUID"展开形式。
- **notify（通知 / 订阅）**：客户端告诉设备"这个特征有变化就推给我"，之后设备主动推送，不用客户端反复询问。
  - 与**轮询（polling）**相对：轮询是"每个 0.5 秒问一次有没有新数据"，简单但费电费带宽。BLE 心率用 notify，RFID 读卡用轮询。
- **断线重连**：连接意外断开后自动重新扫描并连上，保证长时间无人值守运行。
- **bleak**：Python 的跨平台 BLE 客户端库，在 Linux 上通过 BlueZ（系统的蓝牙协议栈，经 D-Bus）与适配器通信。
- **RR 间期**：见第 7 节。

### 5.4 蓝牙命令行工具 `bluetoothctl`

Linux 官方的蓝牙命令行工具。文档中有两个坑，均与"它其实是为交互式终端设计的"有关。

- **bluetoothctl**：BlueZ 提供的交互式命令行工具，逐条输入 `power on`、`scan on` 之类的命令。
- **subprocess**：Python 里创建并控制外部命令的方式（本项目用其异步版本 `asyncio.create_subprocess_exec`）。
- **非交互式 shell**：没有人坐在终端前敲命令，而是一次性把命令喂进去执行完退出。此时 bluetoothctl 会判定"没有交互终端"，`[NEW] Device ...` 这类扫描日志不会被打印出来——于是文档改为**两次调用**：后台启动 `scan on` 等 10 秒（让扫描结果进入 BlueZ 缓存），再用 `devices` 读设备列表（§3.2）。
- **stdout 缓冲（buffering）**：程序的标准输出先攒在内存里、攒够或退出时才真正写出。这正是"看不到实时扫描结果"的直接原因。
- **`stdout=DEVNULL`**：把子进程的输出丢弃，因为我们不依赖它的输出，只依赖它产生的副作用（设备缓存）。
- **`proc.terminate()`**：向子进程发送终止信号，结束那次扫描。
- **`ProcessLookupError`**：进程已经自行退出，再去 `terminate()` 它会报这个错；终止逻辑要容错（§3.2 末尾）。
- **配对流程中的命令**（§3.4）：
  - `power on`：给蓝牙适配器上电。
  - `scan on` / `devices`：开始扫描 / 读取缓存的设备列表。
  - `agent on`：注册**配对代理（agent）**——负责自动应答配对确认请求的程序。
  - `default-agent`：把刚注册的代理设为默认。
  - `pair <addr>`：发起配对。
  - `trust <addr>`：信任设备，之后可自动重连。
  - `connect <addr>`：建立连接通道。
- **`AuthenticationCanceled`**：配对被取消的错误。原因是设备发来配对确认请求时，没有代理（agent）去回应，于是设备侧超时取消，表现为"配对后立即断开"（§3.3）。解决办法是把 `agent on`、`default-agent`、`pair` 三条命令放进**同一个 bluetoothctl 会话**里按顺序执行。
- **`--timeout 30`**：给这次 bluetoothctl 会话设定最长 30 秒，避免命令挂住不返回。
- **`communicate()`**：把输入一次性喂给子进程并等它结束，返回标准输出与错误输出——适合这种"输入固定、跑完即退"的场景。

### 5.5 统一数据包

- **统一数据包格式**：把三类传感器各不相同的输出，套上同一个外壳再发送，下游（云端、前端）处理起来统一。
- **`header` / `payload`**：包头（元信息）与包体（真正的数据）。
- **`packet_id`**：这一包的唯一编号。MQTT QoS 1 会重复投递，接收端据此去重。
- **`device_id`**：哪台边缘设备发出的，多台设备接入时用来区分。
- **`timestamp`**：数据产生时刻（Unix 时间戳，即从 1970 年起的秒数）。
- **`sensor_type`**：`ble` / `camera` / `rfid` 之一，接收端据此分发到不同处理逻辑。

## 6. 传感器、硬件与视觉算法

对应技术文档 §2、§7。

### 6.1 人脸检测与视觉算法

- **OpenCV**：最常用的开源计算机视觉库，处理图像、检测人脸、读取摄像头都靠它。
- **人脸检测 vs 人脸识别**："检测"回答的是"画面里有没有脸、在哪个位置"；"识别"回答的是"这张脸是谁"。本项目只做检测，在设备端算完即丢，不涉及身份。
- **Haar Cascade（哈尔级联）**：OpenCV 自带的老牌人脸检测方法，用预先训练好的 XML 模型（约 900KB）在图像上滑动比对。
  - 优点：不依赖深度学习运行时，x86、ARM 都能跑；640×480 下单帧只要 5–10ms。
  - 缺点：侧脸、遮挡时精度明显下降，而课堂场景学生大多正对摄像头，可以接受。
- **Viola-Jones**：2001 年提出的经典人脸检测框架，Haar Cascade 就属于它。
- **AdaBoost**：一种"把很多不太准的弱判断规则加权组合成一个相当准的强判断器"的训练方法。**弱分类器**是其中每一条简单的判断规则。
- **级联（cascade）**：把若干分类器串成流水线，一层层筛。前几层极快，绝大多数"明显不是人脸"的窗口在头几层就被排除，只有少数可疑窗口才进入后面更精细（也更慢）的层级——这是它速度的关键。
- **积分图（integral image）**：Haar 特征算法中的加速技巧，让"任意矩形区域内的像素和"能在常数时间内算出来，不必逐像素累加。
- **模型文件（XML）**：Haar 分类器把训练好的参数保存在 XML 里，运行时加载即可，不需要训练、不需要 GPU。
- **MediaPipe**：Google 的机器学习视觉库，检测精度更高（深度学习模型，能处理侧脸与遮挡），单帧约 20–30ms。文档中它因 ARM64 支持问题被放弃（§2.3、§7.2）。
- **深度学习运行时**：跑神经网络所需的底层库（TensorFlow、PyTorch 之类），体积大、对硬件与架构支持要求高；ARM64 的树莓派常常没有可用的预编译包。
- **wheel（`.whl`）**：Python 的预编译安装包。有对应平台的 wheel 就能直接装；没有就得**源码编译**——在本机把源代码编译成可执行文件，动辄数小时且容易失败。
- **注意力评分（attention score）**：本项目自定义的 0.0–1.0 指标，综合两个维度——人脸中心离画面中心的距离（越近分越高）、人脸面积占画面的比例（以 15% 为最佳，过小过大都扣分），按 0.6 / 0.4 加权平均。
- **启发式算法（heuristic）**：靠人为设定的经验规则给结果打分，不用训练数据、不需要模型。代价是"够用但不精确"。
- **加权平均**：几项分数各乘一个权重后相加，权重体现各项的重要程度。
- **特征向量（feature vector）**：用很少的几个数字概括一帧画面的关键信息（`face_count`、`attention_score`、`timestamp`），每包约 100 字节；对比原始画面约 300KB/帧。
- **帧（frame）/ 分辨率 640×480 / fps**：视频由一帧帧静态画面组成；640×480 是每帧的像素尺寸；fps 是每秒处理的帧数（本项目固定 10fps）。
  - 10fps 的取舍：低于 5fps 会漏掉学生快速转头这类变化；高于 15fps 时 CPU 占用超过 15%，而精度提升很小。
- **JPEG**：常用图片压缩格式。文档用它估算带宽：640×480 的 JPEG 每帧约 300KB，10fps 即约 3MB/s。
- **带宽（bandwidth）**：网络每秒能传的数据量。3MB/s 会明显占满教室局域网的无线带宽，因此不传视频只传特征。
- **隐私风险**：画面上有学生面部信息，一旦经网络传出就存在泄露可能；只在设备端处理、只传特征向量，是"数据最小化"的做法。
- **CPU 占用估算**：单帧耗时 × 帧率 = 每秒占用的 CPU 时间。5–10ms × 10 帧 = 50–100ms/s，约合单核的 5–10%。

### 6.2 RFID 读卡

- **RFID（Radio Frequency Identification，射频识别）**：利用无线电读取贴有芯片的卡片或标签的技术。校园卡、门禁卡、公交卡都是它。
- **NFC（Near Field Communication，近场通信）**：RFID 家族里工作在 13.56MHz、作用距离几厘米的标准，手机支付与门禁常用。本项目读的卡属于这一类。
- **读卡距离**：Proxmark3 约 10cm，PN532 约 3cm。触摸屏场景下用户本来就把卡贴上去，缩短可以接受。
- **Mifare**：最常见的 13.56MHz 卡芯片家族，校园卡多用它。
- **UID（Unique Identifier）**：卡的唯一序列号，通常 4 或 7 个字节。它本身没有任何语义，只是一串编号。
- **PN532**：一款常见且便宜的 NFC/RFID 读卡模块，支持 I2C、SPI、串口三种接法。本项目用 I2C。
- **SAM 模式（Security Access Module）**：PN532 的一种工作模式；配置为 Normal 模式并进入**寻卡循环（InListPassiveTarget）**后，模块会持续侦测附近的卡片并读取其 UID。
- **I2C（Inter-Integrated Circuit）**：只用两根信号线（SDA 数据、SCL 时钟）就能挂接多个芯片的板级总线，树莓派原生支持。
  - 通俗理解：一条公交线路，每个设备有自己的"站牌地址"，主机报出地址后对应的设备应答。
- **GPIO（General Purpose Input/Output）**：树莓派上那排可编程引脚，I2C 就走在其中两根上。
- **SDA / SCL**：I2C 的数据线与时钟线。
- **smbus2**：Python 通过 I2C/SMBus 与芯片通信的库。**SMBus** 是 I2C 的一个子集，电气与协议规则更严格，PC 与树莓派上的 I2C 接口通常按 SMBus 使用。
- **I2C 地址（7 位 0x24 / 8 位 0x48）**：每个 I2C 设备都有一个地址。同一个地址有两种写法：7 位写法把最低位留给"读/写"标志，8 位写法则把它算进地址里，于是 `0x24 << 1 = 0x48`。
  - 实用差别：`i2cdetect` 显示的是 7 位地址（`24`），而某些底层帧要求填 8 位写地址（`0x48`），看到两串数字不要慌，它们是同一个东西。
- **帧（frame）结构**：PN532 通信的数据包格式。以文档中 SAMConfiguration 命令为例：

  ```
  00 00 FF | 03 | FD | D4 14 | 01 | 17 | 00
  前导码   | LEN | LCS | TFI+命令 | 参数 | DCS | 后置码
  ```

  - **前导码 / 后置码**：固定字节，用来界定一个包的开始与结束。
  - **LEN**：本包的数据长度。
  - **LCS（Length Checksum）**：长度的校验字节，接收方据此判断长度有没有传错。
  - **TFI（Transport Frame Identifier）**：方向标志，`D4` 表示主机发给 PN532，`D5` 表示 PN532 回给主机。
  - **命令码**：`0x14` 就是 SAMConfiguration。
  - **DCS（Data Checksum）**：对 TFI + 命令 + 参数的校验字节，用来发现传输过程中的位错误。
- **DIP 开关**：模块上的小拨动开关，用来选择接口模式。PN532 拨成 I2C 模式的组合是开关 1=OFF、2=ON、3=OFF。
- **供电（3.3V / 5V / mA）**：PN532 必须接 3.3V（GPIO Pin 1）。接 5V 可能短期能用，但会提高损坏模块的风险。它工作电流约 100mA，由树莓派板载稳压器供电即可，无需外部电源。
- **去重窗口**：同一张卡停留在读卡器上会被反复读到，因此规定"同一 UID 在 3 秒内只上报一次"。
- **CardMapper**：把"卡 UID"翻译成"学习主题"（如 `mathematics`、`english`）的映射组件。
- **`edge/data/cards.json`**：映射表文件，支持用户自定义，内置 5 张默认卡片对应数学、英语、科学、历史、编程五个主题。映射可在运行中通过 WebSocket 命令增删，不必重启进程。

### 6.3 被替换掉的硬件

- **Proxmark3**：专业的 RFID 研究与开发设备，能读写、分析多种卡片，但需要专用客户端工具与驱动，功耗也更高。
- **USB 控制器（VL805）**：树莓派 4B 上负责 USB 3.0 的芯片（VIA Labs VL805）。它与部分 USB 设备存在兼容性问题——表现为设备时而掉线、时而识别不出来，Proxmark3 正好踩中这一点。
- **设备枚举（enumeration）**：系统识别并登记一个新接入的 USB 设备的过程；枚举失败就意味着设备根本不出现。
- **换 PN532 的收益**：绕开了 USB 控制器，走树莓派原生的 I2C；功耗从约 500mA 降到约 100mA；代价是读卡距离缩短。

### 6.4 摄像头设备与系统配置

- **`/dev/video0`、`/dev/video1`**：Linux 把摄像头当文件对待，编号就是设备文件结尾的数字。
- **设备号不固定**：部分 USB 摄像头会被分配到 `/dev/video1` 而不是默认的 `/dev/video0`，取决于内核驱动（如 `bcm2835-v4l2`）的加载顺序。
- **`bcm2835-v4l2`**：树莓派上的 V4L2 摄像头驱动模块之一（V4L2 是 Linux 的视频采集设备接口标准）。
- **`v4l2-ctl --list-devices`**：列出系统里所有视频采集设备及其设备号的命令，首次安装时用它确认摄像头在哪。
- **`INNOARK_CAMERA_DEVICE` 环境变量**：用来在不改代码的情况下指定摄像头设备号（对应配置项 `EdgeConfig.camera_device`）。
- **`i2cdetect -y 1`**：扫描 1 号 I2C 总线上的所有地址，用来验证 PN532 有没有接好——看到 `24` 就说明正常。
- **`/boot/config.txt`（Bookworm 起为 `/boot/firmware/config.txt`）**：树莓派的启动配置文件。在里面加 `dtparam=i2c_arm=on` 即可启用 I2C，改完需要重启。

## 7. 生理指标：HR、RR、HRV、RMSSD

对应技术文档 §2.2。这一节是心率那一路的核心概念。

- **HR（Heart Rate，心率）**：每分钟心跳次数，最常见的身体状态指标。
- **RR 间期**：相邻两次心跳之间的时间间隔，单位毫秒（名字来自心电图上那个尖尖的 R 波）。心跳越快，RR 越短。
  - 注意：BLE 心率测量特征里的 RR 值按规范以 1/1024 秒为单位，解析时要换算成毫秒。
- **HRV（Heart Rate Variability，心率变异性）**：相邻心跳间隔的"波动程度"。
  - 通俗理解：人的心跳不是节拍器，两次心跳之间的间隔总在几十毫秒内上下浮动。浮动丰富通常代表身体放松、恢复良好；过于"整齐"往往与紧张、疲劳、压力相关。
  - 为什么用它：只需手环的心跳数据就能估计学生的放松/疲劳状态，不需要额外设备。
- **RMSSD（Root Mean Square of Successive Differences，相邻差值均方根）**：最常用的短时 HRV 指标。算法是：把相邻 RR 的差值逐个平方 → 求平均 → 开方。
  - 数学式：`RMSSD = sqrt( mean( (RR[i+1] - RR[i])² ) )`
  - 为什么选它：只需要加减乘除和开方，不需要做频谱变换，非常适合树莓派这类小机器上的实时计算。
- **时域 HRV 分析**：直接在时间序列上算统计指标（RMSSD、SDNN 等），与需要先做傅里叶变换的"频域分析"相对。
- **RR 缓冲区**：代码里保存最近 10 个 RR 间期的列表，由 `asyncio.Lock` 保护（见 1.4）。
- **5 秒聚合窗口**：不是每收到一个 RR 就上报，而是每 5 秒算一次平均心率与 RMSSD，只推一条。
  - 收益：心率每秒产生 1–3 个 RR 通知，聚合后消息量降到原来的 1/5 ~ 1/15，同时教师端的趋势刷新仍然足够及时。

## 8. 运行环境与运维

对应技术文档 §6.4–§6.6、§7.3–§7.4、附录 A。这部分是"让它能连续跑几个星期不出事"的知识。

- **systemd**：Linux 现在标准的服务管理器，负责开机自启、后台运行、崩溃后自动重启。
- **unit / service 文件**：systemd 的配置单元文件。本项目用它把边缘程序注册成常驻服务。
- **`Restart=always`**：进程不管因为什么原因退出，都自动重新拉起。
- **`RestartSec=5`**：每次重启前等 5 秒，避免瞬间疯狂重启。
- **`StartLimitIntervalSec` / `StartLimitBurst`**：重启频率限制——在 200 秒的时间窗内最多允许重启 10 次，超过就放弃并停止尝试。
  - 为什么需要：硬件故障（摄像头掉线、蓝牙适配器挂死）会让程序反复崩溃，无限重启会刷爆日志并持续占用 CPU。宁可停在"已知失败"状态，等人工介入。
  - 位置提示：这两项写在 `[Unit]` 段；旧写法 `StartLimitInterval` 不带 `Sec`，新版本 systemd 已改名。
- **虚拟环境（venv）**：为项目单独准备的一个 Python 包目录，与系统 Python 隔离。项目在 `/opt/innoark-edge/venv/` 下创建。
  - 为什么需要：Raspberry Pi OS 自带的 Python 里已有若干由系统包管理器（apt）管理的库，直接用 `pip install` 装东西可能与它们冲突，甚至弄坏系统工具。虚拟环境让项目的依赖"关起门来"。
- **rfkill**：Linux 控制无线设备（蓝牙、WiFi）软开关的命令。
- **软阻塞（soft block）**：软件层面把无线设备禁用；`rfkill unblock bluetooth` 就是解除它。蓝牙"扫描不到任何设备"时，第一步应排查是不是被软阻塞了。
- **蓝牙自愈脚本（`scripts/fix-bluetooth.sh`）**：把"解除阻塞 → 重新上电 → 必要时重启服务"这套恢复动作脚本化，可由 systemd 定时任务或 WebSocket 命令触发（§7.3）。
- **nmcli**：NetworkManager 的命令行工具，本项目用它管理 WiFi 连接（`edge/wifi_manager.py`）。
- **日志（log）**：程序运行记录。排查现场问题时，systemd 的日志是主要线索。
- **常驻进程 / 守护进程（daemon）**：在后台持续运行、不占用终端的进程；这也正是文档强调 SQLite"不需要额外守护进程"的原因。
