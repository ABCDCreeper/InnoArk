## 0. 全局

一句话：一台树莓派同时连着心率手环、摄像头和刷卡器，把数据实时推给教室触摸屏上的网页，同时上传云端。

```
采集            汇聚                 本地呈现 / 上云
BLE 手环   ┐                      ┌ WebSocket → 浏览器（教师端）
USB 摄像头 ├→ asyncio 队列 → 广播 ┤
PN532 刷卡 ┘                      └ MQTT → 云端（可离线缓冲）
```

四个贯穿全文的关键词：**异步**（等人时去干别的）、**轻量**（树莓派算力小）、**离线**（教室网络不可靠）、**隐私**（画面不出设备）。

## 1. 编程与并发

**树莓派 4B**：信用卡大小的单板机，担任边缘终端；4 核 ARM + 4GB 内存，性能约相当于低端手机。

**ARM64 / Cortex-A72**：树莓派的 CPU 型号与架构，与 PC 的 x86 不通用——很多库没有 ARM64 的预编译包，这是 MediaPipe 装不上的根因。

**边缘计算（edge）**：把计算放在数据产生的地方（教室里的树莓派），响应快、省带宽、隐私数据不出设备。

**I/O 密集 vs CPU 密集**：时间是花在"等外部返回"还是"算"上。三类传感器都属前者，所以适合异步。

**asyncio**：Python 标准库的异步框架，一棵线程里同时照看多个等待中的任务。像服务员给 A 桌下单后不站在厨房门口等，先去 B 桌，谁好了再回来。（§1.1，`edge/__init__.py`）

**协程 / 事件循环**：协程是用 `async def` 定义、能中途暂停再接着跑的函数；事件循环是决定"此刻轮到谁"的调度台。

**await**：把控制权交还事件循环、等某个操作出结果。调用 `async def` 函数只是造出一个"待办"，必须 await 才执行——§5.2 里 MQTT 消息既不发出也不报错就是这个原因：

```python
await client.publish(...)   # 正确
client.publish(...)         # 错误：协程对象被丢掉，静默失败
```

**协作式并发**：只在代码写了 await 的地方切换，不靠操作系统强行打断；代价是有人写出不 await 的死循环，整个循环都会卡住。

**多线程 / 多进程**：前者共享内存、切换快但要加锁；后者各自独立、通信需序列化和复制。

**GIL（全局解释器锁）**：CPython 同一时刻只允许一个线程执行字节码，多线程在计算场景几乎无法并行，还要平白承担抢锁开销——这是选异步的另一条理由。

**线程上下文切换开销**：线程切换要保存和恢复现场，线程越多纯开销越大。

**跨进程通信（IPC）**：进程间传数据必须经管道/共享内存并序列化；多进程方案里共享队列与设备状态就得额外写这一套。

**生产者—消费者模式**：做数据和用数据的两方中间放一个队列，各自按节奏工作。三个传感器是生产者，WebSocket 广播循环是唯一消费者。

**asyncio.Queue**：异步版传送带，`put` 放、`get` 取；`maxsize=100` 说明它是有界队列。

**背压（backpressure）**：队列满时生产者自然被挡住，内存不会无限增长——像下游堵住的水管，上游灌不进去，而不是把管子憋爆。

**竞态条件（race condition）**：两个执行流插队操作同一份数据，结果取决于谁先谁后，表现为偶发 bug。文档中的例子是心率回调正在写缓冲区、聚合任务同时在读并清空（§2.2、§6.1）。

**asyncio.Lock**：保证同一时刻只有一个协程进入临界区。文档里只锁"拷贝列表"那一小段（微秒级），出锁后再计算和发送，避免影响 BLE 通知的接收。

**快照（copy）**：锁内复制一份数据，出锁后用副本处理，目的是缩短持锁时间。

**asyncio.TaskGroup**：Python 3.11 的语法糖，一组任务统一启动和收尾，其中一个抛错会取消其余任务，不留孤儿任务。

**序列化**：把内存对象变成可传输或存储的形式（这里是 JSON）。广播前的 `json.dumps` 就是它。

**数据类（dataclass）**：专门装一组字段的类；`EdgeConfig` 和各传感器的采集结果都是。

## 2. 后端与数据库

**Flask**：轻量 Python Web 框架。运行内存约 20MB、启动低于 1 秒，适合树莓派（§1.2）。

**蓝图（Blueprint）**：把路由按业务拆到多个文件、再注册回主应用的机制；文档用它组织 10 个以上路由模块。

**WSGI**：Python 里 Web 服务器与 Web 框架之间的标准接口（异步版本叫 ASGI）。`main.py` 让 aiohttp 与 Flask 共用一个进程，靠的就是 WSGI 适配层。

**Werkzeug / Jinja2 / Click**：Flask 的底层 HTTP 工具、模板引擎和命令行解析库；文档提到它们只为说明 Flask 依赖很少。

**应用工厂**：用 `create_app()` 现场组装并返回应用，便于切换配置和写测试，对应 `backend/app/__init__.py`。

**Django / FastAPI**：被对比掉的两个框架。Django 自带 ORM（用对象操作数据库表）、admin 后台、中间件栈，功能全但重；FastAPI 用 Pydantic（声明字段类型、自动校验）定义模型，启动与序列化开销更大。

**SQLite**：一个文件就是一个数据库，不需要独立服务进程；数百用户与项目数据下文件小于 1MB。相比之下 MariaDB/PostgreSQL 要多占 100MB 以上内存和一个常驻进程。

**WAL（预写日志）**：先写日志再择机合并回主库的模式。关键是读不阻塞写、写不阻塞读，所以"多人查询 + 一人写入"可以并存；但写与写仍互斥（写串行化），单次写入低于 10ms 才够用。

**SQLite 线程约束**：连接对象默认只能在创建它的线程使用，跨线程会报 `SQLite objects created in a thread can only be used in that same thread`；起因是 Flask 开发服务器默认多线程。做法是不共享连接——每请求新建、用完关闭（§6.6）。**`g` / before_request / teardown_request** 是 Flask 的请求级临时储物柜与前后钩子，用来建连接、关连接。

**token**：登录成功后服务器签发的凭证，之后每个请求带着它认人，不必重发密码；前端存在 localStorage，所以刷新页面仍保持登录。

**REST / CRUD**：接口设计风格（名词复数表资源、HTTP 方法表动作）与增删改查四类操作，文档用它概括后端业务范围。

## 3. 前端

**Vue 3 / Naive UI**：前端框架与所选组件库。选 Naive UI 是因为支持按需引入（只打包用到的组件）、属性贴近原生 HTML；相应地避开了 Element Plus 的体积和 Ant Design Vue 的样式覆盖问题。

**Vite / ESM / tree-shaking**：构建工具、浏览器原生模块体系与"摇树"（打包时丢掉未被引用的代码）。产物低于 200KB（gzip 后）。

**SPA（单页应用）**：整站只有一个 HTML，切页面由 JS 局部替换——这正是下面路由模式问题的由来。

**Hash 路由**：URL 形如 `/#/projects`，井号之后的内容浏览器不发给服务器，由前端自己解析。好处是服务器只发静态文件，部署在根路径或子路径都不用改配置；代价只是多一个 `#`，而 Kiosk 场景用户从不手输地址。对应 `createWebHashHistory`。

**History 模式**：URL 干净（`/projects`），但服务器必须把未知路径回退到 `index.html`（Nginx 的 `try_files $uri $uri/ /index.html`），部署在子路径时前缀要处处改、容易出错。对应 `createWebHistory`。

**Pinia / store / auth store**：Vue 3 的全局状态仓库；auth store 存放 token 与当前用户。

**导航守卫（navigation guard）**：跳转页面前的检查钩子，用来判断登录与否。§4.3 的坑是它可能在 auth store 初始化完成前误判为未登录，现做法是登录成功后延迟 300ms 再跳转（更正统的做法是监听 store 变化）。

**Nginx**：Web 服务器，负责发静态文件与反向代理。

## 4. Kiosk 终端

**Kiosk 模式**：浏览器全屏运行、无地址栏与标签页的自助终端形态，树莓派开机自动进入（§4.2）。

Chromium 启动参数：`--kiosk` 全屏无边框、`--window-size=1920,1080` 固定分辨率、`--start-maximized` 启动最大化、`--touch-events=enabled` 启用触摸事件。

**unclutter -idle 5**：鼠标 5 秒不动就隐藏指针；不加 `-root` 是为了避免与窗口管理器的权限冲突。

**fonts-wqy-zenhei / fonts-wqy-microhei / fonts-noto-color-emoji**：中文与彩色 Emoji 字体，缺了中文会渲染成方框。

**xset / DPMS**：X 的省电黑屏机制，Kiosk 必须关掉，否则用户第一次走近看到的就是黑屏。

## 5. 通信

### 5.1 WebSocket（本地实时推送）

**HTTP vs WebSocket**：HTTP 是问一次答一次，服务器无法主动推送；WebSocket 是在 HTTP 之上"升级"出来的长连接，之后双方随时可发。建立时先发一个带 `Upgrade: websocket` 的请求完成握手。

**aiohttp / WebSocketResponse / 广播**：实现库、代表单条连接的对象，以及把消息循环发给连接集合的动作。广播集中在一个协程里做，避免多个协程同时往同一条连接写数据。

**ConnectionResetError**：对端突然断开时抛出的异常，捕获后把该连接移出名单。

**心跳与超时是两回事**：服务器每 30 秒 ping 一次确认链路还活着（pong 由底层自动回，业务代码不用管）；某类传感器超过 15 秒没有数据则广播 `sensor_status`，前端标记为断开——前者看链路，后者看设备是否还在产出。

### 5.2 MQTT（上传云端）

**MQTT**：物联网常用的轻量消息协议，发布/订阅模型，像公共公告板——发的人不必知道谁在收。broker 就是那块公告板；topic 是消息地址（本项目为 `前缀/设备号/传感器类型`）。QoS 是送达等级：0 最多一次、**1 至少一次（本项目采用，故需 `packet_id` 去重）**、2 恰好一次。

**离线缓冲与重试**：断网或发布异常时把数据写进本地 SQLite，后台协程每 5 秒检查网络并补发。间隔太短会高频空转白耗 CPU，太长则数据积压；补发失败即 `break`，留到下一轮以保证顺序。

**静默失败**：出错却不报错的现象。这里指的是漏写 `await`，消息既发不出去也没有日志，最难排查——**aiomqtt（旧名 asyncio-mqtt）** 的 `publish()` 正是异步方法。

### 5.3 BLE（心率手环）

**BLE**：低功耗蓝牙，手环、心率带使用的省电协议。**扫描**即在时间窗内监听设备广播；本项目采用两阶段发现——先按心率服务 UUID 精确过滤，找不到再按设备名关键词兜底。

**GATT / 服务 / 特征 / UUID**：BLE 对外暴露数据的标准结构，像一棵树：服务（`0x180D` 心跳服务）→ 特征（`0x2A37` 心跳测量）→ 值，UUID 就是标识它们的十六进制编号。

**notify vs 轮询**：notify 是"有新数据就推给我"（BLE 心率用，省电），轮询是"每隔一阵问一次"（RFID 用）。**bleak** 是 Python 的 BLE 客户端库，Linux 上经 BlueZ/D-Bus 通信。

### 5.4 bluetoothctl 的两个坑（§3.2、§3.3）

**bluetoothctl**：BlueZ 的蓝牙命令行工具，本为交互式终端设计，项目通过 Python 的 subprocess 调用。

**坑一：非交互式下读不到扫描结果**。没有交互终端时 `[NEW] Device ...` 这类日志不会打印（输出被缓冲或抑制）。做法是拆成两次调用：后台启动 `scan on` 等 10 秒让结果进入 BlueZ 缓存，再用 `devices` 读列表。另外进程可能已自行退出，`terminate()` 要容错 `ProcessLookupError`。

**坑二：配对后立即断开（AuthenticationCanceled）**。设备发来的配对确认请求没有代理应答，于是超时取消。修法是把 `agent on`（注册配对代理）、`default-agent`（设为默认）、`pair` 三条命令放进同一个 bluetoothctl 会话按序执行，随后再 `trust`（信任，便于自动重连）和 `connect`（建立连接）。

其余命令：`power on` 上电、`scan on` 扫描、`devices` 读缓存；`--timeout 30` 限制会话时长，避免命令挂住。

### 5.5 统一数据包

把三类传感器各不相同的输出套上同一个外壳，下游才好处理。`header` 装元信息：`packet_id`（MQTT 去重用）、`device_id`、`timestamp`、`sensor_type`；`payload` 装真正的数据。

## 6. 硬件与视觉

### 6.1 人脸检测

**检测 ≠ 识别**：检测只回答"画面里有没有脸、在哪"；识别才回答"这是谁"。本项目只做检测，画面在设备端算完即弃。

**Haar Cascade**：OpenCV 自带的老牌人脸检测，用约 900KB 的 XML 模型，不依赖深度学习运行时，任何架构都能跑，640×480 单帧 5–10ms；代价是侧脸与遮挡精度差。它属于 **Viola-Jones** 框架，靠 **AdaBoost** 把许多弱判断规则加权组合成强判断器，再用**级联**一层层筛：前几层极快，排除掉绝大多数非人脸区域，只有少数可疑窗口进入后面的精细判断——这是速度的关键（另有积分图加速矩形区域求和）。

**MediaPipe**：Google 的视觉库，精度更高（深度学习、能处理侧脸遮挡）但单帧 20–30ms，且在树莓派 ARM64 上装不上：没有 **wheel**（预编译包）就只能**源码编译**，动辄数小时且容易失败。

**注意力评分**：自定义的 0.0–1.0 指标——人脸离画面中心越近、面积越接近画面的 15% 得分越高，按 0.6/0.4 加权。属于**启发式算法**：人为设定的规则，不需要训练数据。

**特征向量**：用少量数字概括一帧画面（人脸数、注意力分数、时间戳），约 100 字节/包，对比整帧 JPEG 约 300KB。640×480、10fps 的原始视频约 3MB/s，既占满带宽又有隐私风险——这是不传视频的原因。

### 6.2 RFID 读卡

**RFID / NFC / Mifare / UID**：射频识别技术；NFC 是其中 13.56MHz 的近场子集；Mifare 是最常见的卡芯片家族；UID 是卡的唯一编号，本身没有语义，靠 **CardMapper** 映射成学习主题（映射表在 `edge/data/cards.json`，可运行时增删）。

**PN532**：常见的 NFC 读卡模块，支持 I2C/SPI/串口三种接法。配置为 **SAM（Normal）模式**后进入寻卡循环，持续侦测卡片。**去重窗口**：同一张卡停留在读卡器上会被反复读到，因此 3 秒内只上报一次。

**I2C / GPIO / smbus2**：只用两根线（SDA 数据、SCL 时钟）就能挂多个芯片的板级总线，走在树莓派的 GPIO 排针上；smbus2 是 Python 侧的通信库（SMBus 是 I2C 的严格子集）。

**I2C 地址的两种写法**：7 位写法把最低位留给读写标志，8 位写法把它算进地址，于是 `0x24 << 1 = 0x48`。`i2cdetect` 显示 7 位（`24`），有些底层帧要求 8 位（`0x48`），其实是同一个东西。

**PN532 帧结构**：以 SAMConfiguration 为例，`00 00 FF | LEN | LCS | D4 14 | 参数 | DCS | 00`——前导码与后置码界定包的边界，LEN 是长度，LCS 校验长度，DCS 校验数据（TFI + 命令 + 参数），`D4` 表示主机发给 PN532（`D5` 为反向），`0x14` 是 SAMConfiguration 的命令码。

**DIP 开关**：模块上的拨码开关，选 I2C 模式的组合是 1=OFF、2=ON、3=OFF。**供电**必须 3.3V（接 5V 可能短期能用但有损坏模块的风险），工作电流约 100mA，树莓派板载稳压器即可带动。

**i2cdetect -y 1**：扫描 1 号 I2C 总线上的地址，看到 `24` 说明连接正常；启用 I2C 需在 `/boot/config.txt`（Bookworm 起为 `/boot/firmware/config.txt`）加 `dtparam=i2c_arm=on` 并重启。

### 6.3 被替换的硬件

**Proxmark3**：专业的 RFID 研究设备，功能强但需要专用客户端工具。它与树莓派 4B 的 **VL805** USB 控制器（负责 USB 3.0 的芯片）不兼容，表现为设备时而掉线、时而**枚举**失败（系统识别并登记新 USB 设备的过程）。换成走 I2C 的 PN532 后绕开了这颗芯片，功耗也从约 500mA 降到约 100mA，代价是读卡距离从约 10cm 缩短到约 3cm。

**摄像头设备号**：Linux 把摄像头当文件对待（`/dev/video0`、`/dev/video1`），编号取决于驱动（如 `bcm2835-v4l2`）加载顺序，未必是 0。首次安装用 `v4l2-ctl --list-devices` 确认，运行时可用环境变量 `INNOARK_CAMERA_DEVICE` 覆盖 `EdgeConfig.camera_device`。

## 7. 生理指标

**HR / RR**：每分钟心跳次数；相邻两次心跳的间隔（毫秒，名字来自心电图上的 R 波）。注意 BLE 心率测量特征里的 RR 值按规范以 1/1024 秒为单位，解析时要换算成毫秒。

**HRV（心率变异性）**：心跳间隔的波动程度。人的心跳不是节拍器，间隔过于整齐常与紧张、疲劳相关，波动丰富通常代表放松、恢复良好——只用一条心率数据就能估计状态。

**RMSSD**：最常用的短时 HRV 指标：相邻 RR 的差值逐个平方、求平均、再开方（`sqrt(mean(diff²))`）。只用到四则运算与开方，适合树莓派实时计算；属于**时域分析**，相对的是需要做频谱变换的频域分析。

**RR 缓冲区 / 5 秒聚合**：代码保存最近 10 个 RR 间期（由 `asyncio.Lock` 保护）；每 5 秒算一次平均心率与 RMSSD 再上报，消息量降到原来的 1/5 ~ 1/15，而趋势刷新仍足够及时。

## 8. 运行环境与运维

**systemd / unit 文件**：Linux 的服务管理器，负责开机自启与崩溃重启；`Restart=always` 表示退出就拉起，`RestartSec=5` 表示每次隔 5 秒。

**StartLimitIntervalSec / StartLimitBurst**：200 秒内最多重启 10 次，超过就停止尝试。硬件故障会让程序反复崩溃，无限重启只会刷爆日志、持续占用 CPU，不如停在已知失败状态等人工介入。（这两项写在 `[Unit]` 段；旧写法 `StartLimitInterval` 不带 `Sec`。）

**虚拟环境（venv）**：给项目单独准备的 Python 包目录（本项目在 `/opt/innoark-edge/venv/`）。系统 Python 里的库由 apt 管理，直接用 pip 安装可能冲突甚至弄坏系统工具，所以关起门来装。

**rfkill / 软阻塞**：Linux 开关无线设备的机制，`unblock bluetooth` 即解除软件层禁用——"扫描不到任何设备"时先查这个。恢复动作封装在 `scripts/fix-bluetooth.sh`，可由 systemd 定时任务或 WebSocket 命令触发。

**nmcli**：NetworkManager 的命令行工具，用于 WiFi 管理（`edge/wifi_manager.py`）。
