# InnoArk 技术文档 · 快速入门

> 五分钟读完，就能看懂《InnoArk（智创方舟）技术文档》在讲什么。这里只保留上手必需的概念，细节回到技术文档对应章节。

## 一、这套系统在做什么

一台树莓派（教室里的"边缘终端"）同时接三类传感器——BLE 心率手环、USB 摄像头、PN532 刷卡器，数据汇总后走两个出口：本地用 WebSocket 推给触摸屏上的教师端页面，同时用 MQTT 上传云端。

```
BLE 手环 ┐
摄像头   ├→ asyncio 队列 → ┬ WebSocket → 浏览器（教室触摸屏）
刷卡器   ┘                └ MQTT → 云端（断网时本地缓存补发）
```

记住四个词，就能解释文档里绝大多数取舍：**异步**（等人时去干别的）、**轻量**（树莓派算力小）、**离线**（教室网络不可靠）、**隐私**（画面不出设备）。

## 二、六个必须先懂的概念

1. **asyncio 与 await**：一个线程里同时照看多个等待中的任务，只在 `await` 处切换。调用 `async def` 函数只是造出一个"待办"，**漏写 await 就什么都不会发生、也不报错**——文档里 MQTT 消息发不出去就是这个坑（§5.2）。
2. **队列与背压**：三个传感器是生产者，广播循环是唯一消费者，中间是 `asyncio.Queue(maxsize=100)`。队列满时生产者自动被挡住，内存不会无限增长。
3. **锁与竞态**：心率数据有两条并发路径（回调写入、聚合任务读取并清空），所以 RR 缓冲区由 `asyncio.Lock` 保护，且只锁"拷贝列表"那一小段（§6.1）。
4. **为什么选轻量栈**：树莓派是 4 核 ARM + 4GB 内存，所以后端用 Flask + SQLite、人脸检测用 Haar Cascade 而不是 MediaPipe、读卡走 I2C 而不是 USB——大框架、深度学习运行时、USB 设备都在这台机器上出过问题。
5. **两个数据出口**：本地 WebSocket 长连接实时推送；上云用 MQTT 发布/订阅，QoS 1 + `packet_id` 去重，断网时把数据写进 SQLite，每 5 秒尝试补发。
6. **部署形态**：前端是 Hash 路由的 SPA，在 Chromium Kiosk 模式下全屏、开机自启；后端程序由 systemd 守护，运行在 venv 里。

## 三、分区速览

### 后端与数据库

- **Flask**：轻量 Web 框架（约 20MB 内存、启动低于 1 秒），路由按业务拆进**蓝图**。
- **WSGI**：Python 的"服务器 ↔ 框架"接口；`main.py` 靠它把 Flask 挂进 aiohttp，两种服务共用一个进程。
- **SQLite + WAL**：单文件数据库；WAL 模式下读不阻塞写，写与写仍串行，单次低于 10ms，50 人以内够用。
- **每请求一个连接**：SQLite 连接不能跨线程使用（Flask 默认多线程），因此每个请求新建、请求结束时关闭。
- **token**：登录后签发的凭证，前端存在 localStorage，之后的请求带着它。
- 被对比掉的方案：Django 自带 ORM/admin/中间件，太重；FastAPI 用 Pydantic 声明模型，启动与序列化开销大。

### 前端与终端

- **Vue 3 + Naive UI**：组件库支持按需引入；配 Vite 打包，产物低于 200KB（gzip 后）。
- **Hash 路由**：URL 带 `#`，服务器只需发静态文件，部署在根路径或子路径都不用改配置；History 模式则要靠 Nginx `try_files` 回退，容易配错。
- **Pinia + 导航守卫**：登录状态存在 auth store；守卫可能早于状态初始化而误判未登录，所以登录成功后延迟 300ms 再跳转（§4.3）。
- **Kiosk 终端**：Chromium 用 `--kiosk` 全屏启动；`unclutter` 隐藏鼠标指针，装文泉驿中文字体，用 `xset` 关掉黑屏节能。

### 通信

- **WebSocket**：从 HTTP 升级来的长连接，服务器可主动推送；每 30 秒心跳保活，某类传感器 15 秒没有数据就广播 `sensor_status`，前端标记为断开。
- **MQTT**：发布/订阅模型，由 broker 转发，topic 形如 `前缀/设备号/传感器类型`；QoS 0/1/2 分别是最多、至少、恰好送达一次。
- **BLE**：低功耗蓝牙，数据按 GATT 树组织——服务 `0x180D`（心率）→ 特征 `0x2A37`（心跳测量），用 notify 让设备主动推送；RFID 那边则是 500ms 轮询。
- **bluetoothctl 的两个坑**：非交互式执行时读不到扫描结果（改为后台扫描 + `devices` 读缓存）；不注册配对代理（agent）会报 `AuthenticationCanceled`，表现为配对后立即断开。
- **统一数据包**：`header`（`packet_id` / `device_id` / `timestamp` / `sensor_type`）+ `payload` 交给下游。

### 硬件与视觉

- **Haar Cascade**：OpenCV 自带的人脸检测，900KB 模型、单帧 5–10ms、任何架构都能跑，靠 Viola-Jones 框架的 AdaBoost 与级联加速；代价是侧脸与遮挡精度差。
- **MediaPipe**：精度更高，但 ARM64 上没有预编译包（wheel），源码编译要数小时且容易失败，故弃用。
- **只传特征向量**：人脸数、注意力分数、时间戳共约 100 字节/包；原始视频约 300KB/帧、3MB/s，既占带宽又涉及隐私。
- **注意力评分**：人脸离画面中心越近、面积越接近画面的 15% 得分越高，按 0.6/0.4 加权，属启发式规则。
- **RFID**：PN532 模块经 I2C 接 GPIO；7 位地址 `0x24` 就是 8 位写法 `0x48`；必须供 3.3V；同一张卡 3 秒内只上报一次；UID 由 CardMapper 映射成学习主题。
- **更换硬件的理由**：Proxmark3 与树莓派 4B 的 VL805 USB 控制器不兼容（掉线、无法枚举），换成走 I2C 的 PN532 绕开，代价是读卡距离从约 10cm 缩短到约 3cm。
- **摄像头设备号**可能不是 `/dev/video0`，用 `v4l2-ctl --list-devices` 确认，可用环境变量 `INNOARK_CAMERA_DEVICE` 覆盖。

### 生理指标

- **RR 间期**：两次心跳之间的间隔（BLE 规范里以 1/1024 秒为单位，解析时要换算）。
- **HRV**：心跳间隔的波动程度，可用来估计紧张与疲劳；**RMSSD** = 相邻 RR 差值平方的平均再开方，只用到四则运算，适合树莓派实时计算。
- **5 秒聚合**：每 5 秒算一次平均心率与 RMSSD 再上报，消息量降到原来的 1/5 ~ 1/15，趋势刷新仍足够及时。

### 运维

- **systemd**：负责开机自启与崩溃重启（`Restart=always`、`RestartSec=5`），并限制 200 秒内最多重启 10 次，避免硬件故障时无限重启。
- **venv**：依赖装在 `/opt/innoark-edge/venv/`，避免 pip 与系统 apt 包互相破坏。
- **rfkill**：蓝牙扫描不到任何设备时先执行 `rfkill unblock bluetooth`；自愈动作封装在 `scripts/fix-bluetooth.sh`。

## 四、关键数字

| 数字 | 含义 |
|---|---|
| 3.3V | PN532 供电电压，接 5V 有损坏风险 |
| 0x24 / 0x48 | PN532 的 I2C 地址（7 位写法 / 8 位写法） |
| 0x180D / 0x2A37 | BLE 心率服务 / 心跳测量特征 |
| 3 秒 / 500ms | RFID 去重窗口 / 轮询间隔 |
| 5 秒 | BLE 聚合窗口，也是 MQTT 重试间隔 |
| 10fps / 640×480 | 摄像头帧率与分辨率（CPU 占用 5–10%） |
| 约 100 字节 / 约 300KB | 特征向量 / 单帧 JPEG，故不传视频 |
| 100 | 队列容量，形成背压 |
| 30 秒 / 15 秒 | WebSocket 心跳间隔 / 无数据超时 |
| 200KB（gzip） | 前端产物，支撑首屏低于 2 秒 |
| 300ms | 登录后延迟跳转，等状态更新 |
| 200 秒 / 10 次 | systemd 重启频率上限 |
| 约 20MB / 小于 1MB | Flask 内存占用 / `innoark.db` 体积 |
| 小于 1 秒 / 小于 50ms | Flask 启动 / 单请求响应（SQLite 场景） |
| 100mA / 500mA | PN532 / Proxmark3 工作电流 |
